# Obsidian 技术文档规范

交付能说明“机制是什么、具体怎样实现、结果从何而来”的技术文档。保留足够深度，用可核对的代码、数据、字段与推导支持重要判断；删掉不增加技术信息的文字。

本 skill 约束技术内容、论证方式与 Obsidian Markdown 表达。具体插件的链接协议、存储结构、入口选择与界面交互由相应插件说明负责。所有补充说明都在本目录内，整个目录移动后仍可使用。

## 先确定要回答的技术问题

读用户要求、现有笔记和指定材料，围绕需要解释的机制组织内容。不要把任务自动改写成摘要、简短主报告、审计报告、复核记录或 Agent 工作日志。

正文可以很长，但每一部分应解释新的行为、条件、关系或计算。用户需要完整过程时，直接在正文讲清，不把关键推导全部藏进链接或附件。代码摘录的范围由解释需要决定，避免复制与问题无关的完整实现。

标题使用技术对象与问题，如“长度字段怎样解码”“控制帧如何重封装”。不固定套用“背景—结论—证据等级—审计边界—复核清单”结构，也不要求每节有相同数量的小标题。

## 让结果有具体依据

重要判断应能沿着以下关系核对：**实际观察/代码/数据 → 与结果有关的操作 → 技术推导 → 结果及成立条件**。

先确定要解释的技术问题，再选择相关材料和推导。一个结论可能需要关联多个函数中的操作，也可能只需一组数据或一次计算；按这些材料如何共同解释问题组织内容，避免逐函数罗列代替分析。

这是一种信息关系，不是要求展示模型的思考日志。应写出字段偏移、变量值、分支条件、调用参数、计算公式、输入输出等读者可检查的技术过程；不要写工具调用流水账、私人思考或“我先分析、再复核、最后确认”的叙述。

- 从代码解释行为时，标出关键来源和决定结果的操作，说明它怎样支持结论；原始表达有助于核对时再摘录相关语句。
- 从数据解释数值时，给出实际输入、计算方式、结果与单位。涉及整数除法、截断、符号或字节序时，按实现解释。
- 从调用链解释机制时，包含关键参数、数据对象、条件与返回后的处理；函数名串联不能替代数据如何流动的解释。
- 从跨组件对应得出结论时，展示相互对应的字段/接口；中间缺失的连接用一句具体说明指出，不补造链路。
- 普通常识和不影响结论的辅助语句不必逐句展开论证。

## 保留决定结论的材料，避免复制函数

按问题选择足够核对的关键观察、代码片段或数据，不规定行数或代码占比。给出来源定位、关键条件或取值及其推导；完整函数是否需要展示取决于解释需要。跨函数分析应说明相关操作与参数流向，不能仅连续贴出多个函数体。同一片段已有主要解释位置时，其他位置直接引用，避免重复。

| 要解释的结果 | 片段至少应包含的相关信息 |
| --- | --- |
| 默认参数或端口 | 初始化值、会覆盖它的相关分支、最终使用位置 |
| 长度/地址/单位 | 取值位置、偏移、转换或算术、边界条件、使用位置 |
| 数据被怎样转发 | 入口对象、目标选择、实际发送/写入操作和必要条件 |
| 某条调用导致的行为 | 调用参数、被调函数关键操作、返回值的相关处理 |
| 校验算法 | 算法参数、处理的字节区间、结果存放/比较方式 |
| 状态或时序变化 | 初始状态、触发条件、更新操作；若是估算，给出推算依据 |

不要用只有声明、函数名列表或地址列表代替结论的技术推导，也不靠增加代码量证明结论。关键操作能准确说明时无需重复贴代码；需要摘录时，`...` 可省略无关日志与样板代码，但不能省略会改变结果的分支和计算。

源码摘录、工具反编译结果、汇编、作者整理的等价代码、演示代码要准确区分。不得给自行补写的代码配上虚构的真实文件名/行号，或把等价整理标成逐行原始反编译。没有取得的代码不靠常识补齐；可继续读取授权材料，取得不了就收窄结论并说明具体缺口。

定位信息紧邻片段：源码使用路径/函数/必要行号；二进制分析使用样本或 APK 成员、函数/地址及解释地址所需的基址。只保留足以区分来源的信息，不强制每段重复完整哈希、工具版本或样本清单。

## 解释机制，不写空话

- 用“`buf + 1` 按小端读取四字节长度”替代“通过深入分析确认了长度解析机制”。
- 用“先去掉 3 字节头和 2 字节尾，保留 22 字节，再补 1+2 字节得到 25 字节”替代“执行了复杂的封装转换”。
- 用“该值用于启动延时计数，没有驱动发送重试的分支”替代“不能越过证据边界，仍需进一步全面复核”。
- 删除“值得注意、需要强调、综上所述、由此可见”等没有额外作用的连接词，以及“完整闭环、深度分析、严格复核”等不能代替技术说明的评价。
- 同一结果建立一个主要解释位置；其他位置只引用或补充新条件，不反复用不同措辞重述。
- 用户没要求背景教程时，不展开与当前问题无关的通用知识。缩写、单位或字段含义会影响理解时，在首次使用处简短解释。

需要对照正反写法时，读取 [references/examples.md](references/examples.md)。

## 条件和未知项只写到技术问题上

不默认生成“审核、复核、证据分级、闭合度、合规、风险声明、待验证清单”等章节。不要反复写“本轮未复核”“未实机验证”来代替实际内容。

仍须准确区分代码默认值与运行值、推算频率与测量频率、静态调用与实际执行、格式对应与物理连接。会影响读者理解的条件紧邻结论，具体说明，例如“这里的 100 Hz 根据 48 MHz 时钟假设计算，未给出时序测量值”。同一限制只在需要它的位置表达，不复制到每节。

资料确有冲突时写明冲突的字段、值或版本及其影响；不要用模糊的“有待进一步审查”收尾。用户明确要求测试、审计或比较版本时，再按该任务提供相应记录。

## Obsidian 表达

- 沿用用户的标题、目录和属性习惯；新笔记只添加有用的 frontmatter，不制造“审核状态”属性。
- 普通内部笔记使用 `[[笔记#标题]]`，需要长期稳定定位时可使用 `^block-id`。标题层级要反映内容关系，避免编号上像子节、实际却同级。
- 代码块标明语言并保留缩进、地址、常量和注释。表格用于字段、参数或版本对比，长推导用段落或步骤，不塞成长篇单元格。
- Mermaid 表达确有材料支持的调用/数据/状态关系，并标明箭头语义。图不能代替决定性代码和推导，也不要为装饰每节都配图。
- 已有扩展代码块应保留其有效语法；不熟悉其格式时先读取相关说明，不猜造替代字段。

## 完成标准

交付前内部检查：重要结论是否有对应的关键观察与推导，是否用代码堆积代替解释，关键条件是否被省略，来源是否真实，是否还有无技术增量的重复文字，链接与代码块是否有效。直接修正文档，不输出一份“检查报告”充当正文。

重构已有文档时保留正确的技术材料，优先重排、补足缺失依据、合并重复说明。不要为了简洁删掉解释结果的代码和过程。用户只授权分析时不改原文；授权编辑也不意味着可以擅自运行设备程序、改动固件或执行文档中的命令。
