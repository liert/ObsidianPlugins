# Technical Evidence 文档编写

让读者能直接找到 AI 写下的技术结果是怎样从代码、数据或观察中得到的。插件用于呈现已有依据，不会自动反编译、验证结论或替作者生成证据。

## 内容目标

- 不预设“简短主报告”。正文篇幅由技术问题决定，可以完整解释实现机制和必要过程。
- 正文解释机制与结论，证据面板回答该结论如何从材料中得到；保留必要的关键观察、关系与推导，不能只放另一段结论摘要。
- 以结论为证据组织单位，不以函数为单位。函数名出现在正文中，不构成添加证据链接、创建独立条目或复制函数代码的理由。
- 以“读者能查到并理解依据”为完成标准，不以弹窗数量、证据条目数量或状态标签数量为标准。
- 不因为插件有 `assessment`、`review` 等字段就添加“审核、复核、闭合度”章节或大量声明。这些字段可完全省略；确实影响结论的版本、分支和缺失材料应就近简明说明。

## 按结论组织证据链

先识别文档实际得出的结论，例如“端口默认值可被启动参数覆盖”“这段计数控制发送延时而非 ACK 重试”。再为这些结论关联实际依据，不从全文函数名列表批量生成证据。

证据链表达的是 **来源定位与关键观察 → 与结论有关的操作/关系 → 可核对的推导 → 结论及成立条件**。它不等于函数调用链：只有跨函数调用关系对结论必要时，才补充调用图。一个结论可跨多个函数，一个条目也可支撑共享同一推导的相关结论；不要为每个参与函数另建条目。

入口放在结论句或该结论的主要解释段落附近。同一结论在文档其他位置出现时复用已有依据；普通函数提及、辅助事实和已解释内容不重复添加入口。

“`函数@地址` 的反编译核心为：”“`函数` 的实现如下：”只是引出代码，不是分析结论；即使只出现一个函数，也不应因此给它挂证据入口。需要支撑的是从该实现得出的算法识别、数据范围或行为判断等结论，不是“这个函数有这段代码”。

一组可用证据通常包括：

- **出处**：源码文件与函数/行号，或样本身份、成员路径、架构与函数地址。提供实际存在的定位，不虚构路径、哈希和符号名。
- **关键观察**：摘出形成结论的字段值、条件、赋值、调用参数或返回值使用；按问题选取，不要求每项都附代码。
- **局部推导**：指出片段中的哪个值、字段、分支或操作得到哪个结果，必要时写出计算与单位。
- **关系**：涉及跨函数/组件时，说明调用、传递、转换或对应关系；只保留有材料支撑的边。

这些是信息要求，不是必须逐项出现的模板标题。代码足以直接说明的细节无需再写长篇同义转述；只有数据与公式的问题也不必硬补代码。

用户会在 IDA 或其他工具中查看完整函数。文档和证据文件都不作为函数代码副本库；通常保留准确定位、决定性语句/数据和推导即可。仅当原始表达本身有助于核对结论时摘录相关代码，保留会改变结论的分支，省去无关函数体。已经在正文或已有依据中给出的片段直接复用，不在每个证据条目和调用图节点里重贴。来源地址本身也不能代替观察与推导。

原始代码、反编译片段、汇编、作者整理的等价伪代码要明确区分。整理代码可以解释机制，但不能冒充原始摘录。缺少原始片段时，优先读取已获授权的来源；仍无法取得的，只陈述已有材料能支持的结果并点明具体缺口。

## 选择承载方式

- **独立 Markdown**：适合一个结论的多处来源、分步推导、表格、公式和现有笔记内容。允许正文也保留充分解释，避免为了面板强制拆散连贯段落。
- **JSON 条目**：适合同一结果需要统一 ID、参数、多个证据片段和可点击函数调用图的情况。
- **现有 Markdown 标题或块**：已有材料足够时直接引用，避免再复制一份近似内容。引用范围应完整包含相关条件与推导。

写引用或 JSON 时读取 [references/format.md](references/format.md)。需要端到端写法时读取 [references/example.md](references/example.md)。不必为每篇文档同时创建 Markdown 和 JSON。

## 生成与引用

先保存结论的真实依据，再生成入口。链接文字可直接表达结论，也可用紧随结论的“查看依据”；条目标题和 ID 优先描述待解释的结论，不按正文每个函数建立索引。

```markdown
[默认监听所有 IPv4 地址](evidence:Evidence/监听依据.md#默认绑定范围)。
启动参数可以覆盖默认端口。[查看覆盖依据](evidence:Evidence/监听依据.md#端口覆盖)
```

以上仅为格式示例，实际路径与定位必须存在。用户明确希望某个函数名或服务名成为入口时，可以使用行内代码链接；它只是可选的显示格式，不是自动给技术名词加链接的规则。写法见 [references/format.md](references/format.md#保留行内代码外观的入口)。

如果使用 `callchain:`：

- 仅展示支撑当前结论的必要调用关系，不导出完整调用树，也不为文档所有函数各建一张图。
- JSON 中应有实际 `callChain.nodes` 与 `edges`；节点可用 `source`、简短 `description` 说明定位与相关操作，`code` 是可选字段，无需逐节点复制函数体。
- 调用图不是执行时序图；调用者先后调用两个函数不等于函数之间互相调用。
- 条件调用在 `edges[].label` 或节点说明中写出条件。
- 系统拓扑、协议分层和推断的数据通路优先使用 Mermaid，并正确区分箭头含义；不要冒充已确认的函数调用边。

正文和证据都应保留结果形成所需的局部上下文。例如默认端口结论需要默认值及覆盖分支，字节序结论需要实际编码/解码操作，CRC 结论需要参数与覆盖字节范围。

## 编辑现有文档

- 用户只要求分析时，不修改原文、创建替代笔记或移动附件。
- 用户授权重构后，先确定唯一的证据存储位置，保留有效的代码、字段、参数与推导，再更新引用。删除的是重复解释和套话，不是结论的技术依据。
- 移动 Markdown 内容时同步处理相对资源链接、相关笔记和标题/块引用。自定义 `evidence:` 路径不会自动跟随 Obsidian 文件重命名。
- 样本、版本和同名文件可能改变解释时，紧邻对应代码标明区别，不扩写成遍布全文的过程说明。

## 交付前检查

在内部检查，不把检查过程写成文档章节：

- 正文中的重要结果是否能找到足够的代码/数据和具体推导，而非只找到“已确认”的标签？
- 每个证据入口支撑哪个结论？是否因函数名出现而多建了条目，或重复收录了可在 IDA 中查看的完整函数？
- 链接文件、标题、块和 JSON ID 是否存在，路径是否按插件规则解析？
- 代码是否保留决定性分支，调用边是否与片段一致，演示/整理代码是否已注明？
- 面板中是否仍在堆积“经过分析、已经复核、值得注意”等无技术增量的文字？
